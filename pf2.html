01 / 项目概览

一句话说清这个产品

学生论文写作的真正痛点不在"写不出"，而在"写完之后"——查重降不下来、AI 检测亮红灯、 导师意见不知怎么改、投稿心里没底。市面上的工具只解决单点（查重 / 降重）， 没有人把"降重降 AIGC → 投稿前审查 → 导师批注 / 审稿回复"做成一条闭环。 本产品就是切这个空白地带。

03 / 功能设计

三大核心功能

每个功能都对应一个具体的失败场景，而不是"AI 能做什么"。

1. 降重 / 降 AIGC 核心已上线

场景：查重报告标红 / AIGC 检测亮红灯，自己改又改不像人写的。

  • 平台风格适配：支持知网、维普、万方、Turnitin、GPTZero、格子达 6 类检测平台的改写风格匹配
  • 去 AI 痕迹约束：通过 System Prompt 强约束禁用逻辑连接词与模板句式，保留专业术语与实验数据
  • 逐句对照：改写结果按句对齐展示，标注「已修改 / 新增 / 删除」，而非给一整坨替换结果
输入
结果 · 逐句对照

2. 投稿前审查 核心已上线

场景：论文写完了，投出去之前心里没底，又找不到人帮忙看。

  • 多平台审稿口径：模拟 ACL/EMNLP（NLP 顶会）、SCI 一区/二区、CSSCI/北大核心、CSCD 共 6 类期刊的审稿视角
  • 结构化审稿报告：输出「总体评价 / 主要问题 / 优点 / 修改建议 / 规范意见」五段式，而非一段长文本
  • 严重度分级：问题按 Critical / Major / Minor 分级并彩色高亮，每条附「针对此条去修改」直连修订页
审稿报告核心设计：把 AI 的自由文本输出"翻译"成可操作的结构化清单，用户能一眼看到"最致命的问题是哪几条"。

3. 论文修改 核心已上线

场景：收到导师批注 / 审稿意见，不知道从哪下手，也不知道怎么回复。

  • 三场景分流：导师意见修改 / 审稿反馈修改 / 自我修改，不同场景走不同的 Prompt 与输出结构
  • Response Letter 生成：审稿场景自动产出逐条回复信 + 修改后论文 + 逐条修改说明
  • 修改对照表：将"修改前原文 ↔ 修改后文本"逐段对齐，让用户能快速核对 AI 改了什么
  • 带批注 PDF 导入：支持直接上传导师批注过的 PDF 自动解析
论文修改三场景标签页——同一个入口，根据用户所处阶段切换完全不同的处理逻辑。

05 / 产品决策

三个关键产品判断

这部分是我认为比"做了什么功能"更值得讲的东西——为什么这么选。

决策一 · 为什么不做本科查重？

放弃红海，切"投稿前"这个空白环节

背景：调研 11 款竞品后发现，查重 / 降重赛道已是红海——PaperYY 靠免费查重引流、知网靠官方背书垄断、格子达按论文类型分层定价。作为个人产品，在这个赛道拼价格和渠道完全没有胜算。

判断：但"投稿前审查 + 导师批注协作 + 审稿回复"这个环节，没人做成闭环。笔灵是广度覆盖的"什么都有"，ReadPaper 只有"模拟同行反馈"一个单点，都停留在"给个反馈"而没有落到"帮你改完并回复"。

→ 结果：产品定位从"论文查重工具"转向"论文投审协作工具"，以"投稿前一体化审查"作为差异化拳头功能。
决策二 · 为什么把 AI 输出拆成结构化字段？

不做"聊天框吐长文本"，做"可操作清单"

背景：最早的实现是让 AI 输出一份完整的审稿报告文本，直接铺在页面上。实际用下来发现用户根本抓不住重点——一屏密密麻麻的文字里，"哪条最致命"完全看不出来。

判断：AI 产品的核心不是"生成内容"，而是"把生成的内容转化成用户的下一步动作"。所以把输出改造成了带标记的分段结构，后端按标记解析出结构化字段，前端按严重度彩色高亮展示。

→ 结果：审稿报告从"一段文本"变成"分级问题清单"，每条问题配「针对此条去修改」按钮，直接跳转到修改页——把审查和修改打通成一条链。
决策三 · 为什么砍掉费用预估、风格选择、模型选择？

减少决策摩擦，输入后直接执行

背景：初期版本在用户提交前会弹出"预估费用确认"，还提供三种修改力度、多个模型选择。看起来是给了用户掌控感，实际是让用户在还没看到任何结果前，先做了一堆自己无法判断的选择。

判断：用户来这里是解决问题的，不是来配置参数的。这些选项对用户来说都是"我不知道该选什么"的负担，而且增加了操作步数，直接拉低了任务完成率。

→ 结果：删去费用确认步骤、加急、修改风格与模型选择，改为输入后直接执行。用户只需要"粘贴内容 → 拿到结果"两步。
06 / 平台能力

支撑产品运转的完整体系

  • 账号与安全：邮箱验证码注册（校验真实邮箱，防虚假注册）、JWT 登录、密码加密存储
  • 点数体系：按"固定基础价 + 字数浮动"计费，消费流水可追溯，余额不足时提醒
  • 订阅权益：订阅用户每日免费额度 + 辅助功能折扣，到期时间校验
  • 结果导出：改写 / 审查 / 修改结果支持导出 Word / PDF / Markdown
  • 文件导入：Word / PDF / TXT 导入自动提取文本，支持带批注 PDF 解析
  • 体验细节：全站暗色模式、移动端适配
07 / 边界与反思

哪些做了，哪些还没做

我认为作品集里说清楚"没做成什么"比只列成绩更有价值——这能体现对工程可行性的判断力。

真实用户数据暂无产品已上线可访问，但尚未推广，暂无真实用户与付费数据

做完之后的反思

1. 一个人做产品，最大的风险不是技术，是"没人来用" 整个项目我最投入的是功能打磨和体验细节，但事后复盘发现，产品的技术完成度和商业验证之间是断开的——没有真实用户反馈，所有的"体验优化"本质上都是我的自嗨。如果重来一次，我会先把最核心的降重功能做到能跑，就立刻找 10 个真实学生去用，用反馈决定下一步做什么，而不是自己闷头把 8 个功能都做完。
2. AI 产品经理的核心能力，是把"模型能力"翻译成"用户动作" 这个项目里我做的最有价值的一件事，不是调出更好的 Prompt，而是意识到 AI 吐出的长文本对用户没有价值——用户要的是"我现在该干嘛"。把输出结构化、加严重度分级、加"针对此条去修改"的跳转，这些产品设计层面的工作，比模型能力本身更影响体验。
3. 对"能落地"要有更严格的判断 架构文档里规划了多模型路由、Dify 工作流编排这些看起来很专业的设计，但实际落地时都没跑通，最终全部退回最朴素的直连实现。这让我意识到，作为产品经理在规划方案时，应该先验证技术可行性，再写进方案——否则方案再漂亮，也只是纸面功夫。
